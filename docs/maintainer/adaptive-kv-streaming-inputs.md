## 附录 A：参考文章全文

标题：在 16G 显存上运行 Qwen 27B 并启用完整上下文长度：为 llama.cpp 构建自适应 KV 缓存流
作者：黄瑞文（Raymond Huang）
日期：2026-08-28
原文：https://medium.com/@raymond860909/running-qwen-27b-on-16g-vram-with-full-context-length-building-adaptive-kv-cache-streaming-for-bf1e819116e9

说明：以下为原文全文，按所有者提供的文本逐字保留（含小节标题与顺序），只做三件事：去掉导航、
订阅和广告；修正机翻的明显错字（逐处列在文末"转录说明"）；正文陈述一个字未删。

### 引言

如今，要自托管一个功能强大的 AI 代理逻辑模型（LLM），需要一台昂贵的机器。一台 DGX Spark 售价
约为 4000 美元。一台配备 36GB 统一内存的 Mac 约为 2500 美元。即使是二手的 RTX 4090 显卡，配备
24GB 显存，价格也可能超过 2000 美元。

如果你只有一块显存容量为 16GB 或更低的显卡，你的选择基本上只有两种：要么是 10B 级的 dense 模型，
要么是 30B 级的 MoE 模型，但只有少数几层需要交给 GPU 处理。

如果你真的想把一个 300 亿参数的模型塞进一张 16GB 的显卡里，情况很快就会变得非常糟糕。你可能
不得不把量化级别降到 Q2，牺牲相当一部分模型质量，并且把上下文窗口缩小到对于一个严肃的 AI
代理来说都变得不切实际的地步。

但是，如果我告诉你，你实际上可以在 16 GB 的显卡上运行 Qwen3.8 27B，使用 Q3 XL 或 IQ4 量化，
上下文长度最高可达 256K，而且 llama.cpp 不会在运行过程中崩溃，你会相信吗？

以下是我在我的 RTX 5070 Ti 上运行 Qwen 3.8 27B，量化级别为 UD-Q3-XL，上下文大小为 262K，
缓存大小为 Q8K，V 缓存大小为 Q4 的结果：

- 8K 上下文下速度约为 50 tok/s
- 49K 上下文中约 40 tok/s
- 在 114K 上下文中，速度约为 30 tok/s
- 176K 上下文中约 20 tok/s
- 即使在 253K 上下文中，我仍然能获得 ~10 tok/s！

这怎么可能呢？

在深入探讨使 llama.cpp 能够正常工作的修改之前，让我先回顾一下我是如何实现的——我尝试过的事情、
失败的事情，以及最终演变为自适应 KV 缓存流的想法。

### 头痛

我的 mini-ITX NAS 里装了一块 RTX 5070 Ti 显卡。我最初安装它是为了在通过 Nextcloud 应用串流
视频时进行实时转码，以及在有新照片上传到我的 NAS 时运行人脸识别功能。

大多数时候，GPU 都处于闲置状态。偶尔，人脸识别定时任务会占用大约 2GB 的显存，而 FFmpeg 转码
会占用另外大约 3GB。这完全没问题，因为 16GB 的显存足以同时处理这两个任务。

但当我开始使用本地 LLM 时，情况就发生了变化。

通常情况下，我可以运行一个 Qwen 35B MoE 模型，并将尽可能多的层卸载到 GPU 上，直到 16 GB 的
显存耗尽。但当我运行 llama.cpp 服务器的同时，如果又启动了人脸识别或转码任务，问题就出现了。
突然之间，所有进程都争用了相同的显存，最终导致某个进程因内存不足而崩溃。

显而易见的解决方案是为这些偶尔执行的任务预留大约 5 GB 的显存。但这意味着要减少卸载到 GPU 的
LLM 层数，并缩短上下文长度，从而使 llama.cpp 服务器占用大约 10 GB 的显存。

我完全不觉得那是个理想的选择。

于是我开始思考：如果 NVIDIA 有一种机制，允许单个进程在没有其他进程需要时使用所有可用的 VRAM，
但当另一个进程突然需要空间时自动驱逐一些内存页，而不会导致 llama.cpp 服务器崩溃，那会怎么样？

### 显存超额订阅

基本上，我想要的是类似于普通 PC 上的分页/交换机制：程序可以占用过多的物理 RAM，而操作系统会
自动将暂时未使用的内存页移动到磁盘，并在再次需要时将其恢复。

所以我做了一些研究，看看这种机制是否真的存在。幸运的是，我发现 llama.cpp 已经通过
`cudaMallocManaged` API 利用 CUDA 统一内存提供了非常接近我想要的功能。当
`GGML_CUDA_ENABLE_UNIFIED_MEMORY=1` 设置了该选项时，llama.cpp 会使用 `cudaMallocManaged`
统一内存进行 CUDA 内存分配，从而允许在显存耗尽时将内存溢出到系统内存中。这真是个好消息！

所以我将这些层卸载回 GPU，让 llama-server 再次使用几乎全部的 16 GB VRAM，并在启动服务器时
启用统一内存。

结果非常棒。启用这个环境变量后，我看到 llama-server 使用了近 15.8 GB 的显存，同时保持了正常的
预填充和解码速度。然后，当 FFmpeg 转码或人脸识别任务启动时，这三个进程都能持续运行，没有崩溃。
唯一的缺点是 llama-server 的预填充和解码速度暂时显著下降，但一旦这些任务完成，速度就立即恢复
正常。

这时，我原本的头痛基本治愈了。

但我并不满意。

事实上，我在显存超额分配方面有点贪心了。

如果我使用更大的模型和更长的上下文来运行 llama-server，而这个模型和上下文本身就需要超过 16 GB
的 GPU 内存，那会怎么样？

### 以 UVM 模式运行 27B 模型和完整上下文

我第一次尝试启动一个支持 UVM 的 llama-server，使用 Qwen 3.8 27B Q4_K_XL 模型，上下文大小为
262,144。服务器几乎立即崩溃，因为它无法完成预热，因为模型的所有权重都没有驻留在显存中。
Q4_K_XL 模型本身就已经超过 16 GB 了。

接下来，我切换到相同的 Qwen 模型，但量化级别改为较小的 UD-Q3_K_XL，其权重约为 13 GB。这次
服务器成功启动，预填充和解码也都正常工作。起初，性能看起来一切正常。

然而，随着上下文长度的增加和显存逐渐被占用，解码速度显著下降。

问题在大约 120K 上下文时变得明显。此时，模型权重和整个 KV 缓存无法同时放入显存中，页面抖动
开始发生。

UVM 无法判断哪些内存页对 llama.cpp 的解码性能更为重要。它可能会驱逐一些 GPU 几乎立即需要的
模型权重或键值缓存页。这些页面随后必须迁移回显存，在此过程中可能会强制其他仍然需要的页面被
驱逐。

结果是 VRAM 和系统 RAM 之间不断地来回迁移——解码性能开始下降。

我尝试使用 `cudaMemAdvise` API 给 CUDA 一些关于如何处理权重和 KV 缓存页的提示，但这并没有对
性能产生任何实质性的影响。

到目前为止，对于 GPU 来说，如果显存不足以同时运行具有较长上下文的大型密集模型，那么普通的 UVM
似乎不太实用。

但随后我脑海中浮现出一个想法：

如果我自己处理页面加载和驱逐逻辑呢？

### 在 VRAM 中定义驱逐策略

为了确定最佳寻呼策略，我们首先需要了解 LLM 解码过程的一些特点：

LLM 模型，尤其是在 Qwen3 系列中，包含多个层。有些模型使用线性注意力机制，其中键值缓存不会随
上下文长度增长；而另一些模型则使用完全注意力机制，其中键值缓存随上下文长度线性增长。

解码令牌时，这些层是按顺序处理的。每一层都必须等到前一层处理完毕才能开始计算。

由此可见，除了模型权重之外，全注意力层的 KV 缓存占据了不断增长的内存空间的大部分——而这正是
我们在不使用时想要清除的内容。

更重要的是，每一层的键值缓存仅在该层进行计算时才会被访问和更新。一旦该层完成对当前词元的计算，
其键值缓存就会保持闲置状态，直到解码下一个词元时再次到达同一层才会被使用。

这意味着一旦某一层完成计算，其 KV 缓存就可以安全地从 VRAM 中移除，从而为其他层的 KV 缓存
释放空间。

当然，驱逐缓存只是问题的一半。我们还需要将被驱逐的键值缓存重新加载到显存中，才能使其对应的层
再次开始计算。

但是，将键值缓存从系统内存复制回显存需要时间。如果我们等到 GPU 真正需要它时才开始传输，GPU
就必须等待复制完成。为了避免这种停顿，我们需要提前将键值缓存预取到显存中，同时让 GPU 继续计算
其他层。

这些要求实际上可以得出一个结论：

我们需要在显存中设置一个环形缓冲区。

### VRAM 中的环形缓冲区用于 KV 缓存流式传输

VRAM 中的环形缓冲区允许我们在生成每个令牌期间跨多个层重复使用相同的 VRAM 空间。

对于 Qwen3.5–27B，生成一个 token 需要经过 16 个全注意力层。假设我们有一个环形缓冲区，它有
四个 VRAM 插槽——P₁、P₂、P₃ 和 P₄，每个插槽都足够大，可以容纳一个全注意力层的 KV 缓存。

当第一个全注意力层开始计算时，P₁ 已经包含它需要的 KV 缓存 C₁。P₂、P₃ 和 P₄ 分别包含 C₂、
C₃ 和 C₄。

第一层计算完成后，计算会转移到第二层，此时 P₂ 中的 C₂ 正在被使用。与此同时，C₁ 在下一个
token 出现之前不再需要，因此我们可以将 C₁ 从 P₁ 中移除，并将第五层的 KV 缓存 C₅ 预取到
现在空出的槽位中。

在处理第 2、3 和 4 层时，也会发生同样的情况。理想情况下，当第 5 层开始计算时，C₅ 应该已经
加载到 P₁ 中，这样 GPU 就不必停顿等待。

起初，我们似乎可以简单地将这个想法扩展到整个 KV 缓存：只在 VRAM 中保留一个小的工作集，并通过
环形缓冲区流式传输每一层的 KV 缓存。

不幸的是，PCIe 带宽很快成为下一个瓶颈。

PCIe 5.0 ×16 的理论带宽约为每个方向 64 GB/s，但实际有效传输带宽要低一些。在我的系统上，我测得
的带宽约为 50 GB/s。

如果我们将系统 RAM 中的每个 KV 缓存都流式传输到 VRAM 中，并针对每个生成的令牌进行传输，那么
我们的最大令牌生成速率最终将接近以下值：

    每个令牌的 PCIe 带宽 / KV 缓存大小

考虑到 Q8 K / Q4 V 缓存容量约为 100K，Qwen3.5–27B 的总 KV 缓存容量约为 2.5 GB。在约 50 GB/s
的有效 PCIe 带宽下，这大致可以得出以下上限：

    50 GB/秒 ÷ 2.5 GB ≈ 20 托克/秒

而且这还没算上任何额外的传输和同步开销。

问题在于 GPU 本身的计算速度远不止于此。如果我们尝试在每个令牌上都流式传输整个键值缓存，GPU
最终只会再次等待 PCIe 数据传输。我们解决了显存容量问题，却又引入了带宽问题。

所以我们不能简单地把整个 KV 缓存变成一个大的环形缓冲区，然后通过 PCIe 传输所有内容。

我们需要仔细确定在每个上下文长度下应该流式传输多少键值缓存。只有一部分缓存应该在系统内存和显存
之间移动，其余部分则驻留在显存中。这样，较小的预取操作也能跟上 GPU 计算速度，而无需让 GPU 等待
PCIe 接口。

### 具有自动重新分区功能的自适应 KV 缓存流

当上下文数据量还很小时，整个键值缓存都能装入显存中固定的键值缓存空间。此时，没有必要进行任何
数据流传输——环形缓冲区可以保持禁用状态。

当上下文扩展到超出这个固定范围之外时，事情就变得更有趣了。

这时，我们需要为环形缓冲区腾出空间。但这些空间必须来自某个地方。扩大环形缓冲区意味着要从显存
中移除一部分键值缓存。这些被移除的部分现在必须在每次计算其对应层时从系统内存中加载。

这就造成了一种权衡取舍。

我们希望环形缓冲区足够大，能够提供足够的预取槽，以便 KV 缓存能够在 GPU 到达需要它的层之前完成
预取。

但我们也希望它尽可能小，因为我们驱逐的每一个驻留 KV 缓存都会在每个令牌上产生额外的 PCIe 流量。
流式传输越多，每一轮预取所需的时间就越长。

基于这种权衡，我实现了驻留 KV 缓存和流式环形缓冲区之间的自适应重新分区策略：

1. 尽可能保持所有数据驻留。只要固定的显存空间能够容纳整个键值缓存，环形缓冲区就保持禁用状态。
2. 当需要进行流式传输时，从小规模开始。一旦键值缓存不再容纳数据，我就从驻留缓存中释放一小部分，
   并将这些缓存公平地分配到各个全注意力层。释放出来的显存将成为由流式传输层共享的环形缓冲区。
3. 仅在必要时才扩展环形缓冲区。随着上下文的不断增长，每个流式传输的键值区域都会变得更大，预取
   时间也会更长。最终，现有的环形缓冲区可能无法提供足够的预读空间来弥补这种延迟。当这种情况发生
   时，我会从驻留的键值缓存中移除一小部分，并使用新释放的空间来扩展环形缓冲区。

到目前为止，这听起来相当理想：一开始不使用环形缓冲区，然后只有当预取无法跟上时才逐渐增加 VRAM。

但有一个重要的限制。

随着上下文长度的增加，每个令牌流式传输的键值缓存数据量也持续增长。最终，PCIe 带宽本身成为瓶颈。
预取耗时更长并非因为环形缓冲区太小，而是因为我们已经通过 PCIe 总线传输了过多的数据。

而问题就在这里：如果我们再次扩大环形缓冲区，就必须驱逐更多的驻留键值缓存。这意味着每个令牌上
都需要传输更多的数据，这会给 PCIe 带来更大的压力。如果我们继续这样做，就会陷入恶性循环：

    更大的环形缓冲区 → 更少的驻留键值对 → 更多流式传输 → 更高的 PCIe 利用率
    → 更长的预取延迟 → 更大的环形缓冲区

最终，几乎整个固定 KV 空间都会变成环形缓冲区，所有 KV 缓存都会被流式传输，解码速度将完全受到
PCIe 带宽的限制——这正是我们想要避免的情况。

因此，重新分区策略还需要一条额外的保障措施：

只有在增大环形缓冲区仍有助于隐藏预取延迟的情况下才进行增长。如果 PCIe 带宽已饱和，则停止增大
环形缓冲区。

### 结果

在 llama.cpp 中实现了自适应 KV 缓存流后，我再次运行了预填充/解码基准测试——这次将我修改后的
版本与标准的 llama.cpp 进行了直接比较。

为了公平起见，两台服务器均在相同的环境和配置下进行测试：

基准测试设置

- 操作系统：Ubuntu 24.04
- 内核：Linux 6.14
- 内核参数：`iommu=pt`
- 显卡：RTX 5070 Ti 16 GB
- 型号：Unsloth Qwen 3.8 27B
- 量化：UD-Q3-K-XL
- KV 缓存：Q8K/Q4V
- 上下文大小：`--ctx-size` = 预填充长度 + 256
- 解码基准测试：256 个生成令牌的平均解码速度

对于每个数据点，我预先填充了 N 个令牌，设置 `--ctx-size` 为 N + 256，生成了另外 256 个令牌，
并记录了这 256 个令牌的平均解码速度。

结果非常惊人：

在上下文大小达到约 120K 之前，两个版本的 llama.cpp 的性能几乎完全相同。这很合理：整个键值缓存
仍然能够放入显存，因此我的流式传输机制暂时无需工作。解码速度的逐渐下降仅仅是随着上下文大小增加，
计算负载增加的预期效应。

大约 120K 之后情况会发生变化。

此时，默认的 llama.cpp 开始过度占用显存，而我的实现中的环形缓冲区开始发挥作用。随着 UVM 页面
抖动的开始，默认服务器的解码速度迅速下降。

而我的实现方式则几乎沿着同样的稳定坡度继续进行。

这正是我想要看到的。这意味着环形缓冲区和前瞻预取成功地将大部分内存到显存的传输延迟隐藏起来，
使其对 GPU 无害。从 GPU 的角度来看，流式键值缓存的行为几乎就像它仍然驻留在显存中一样。

即使在 200K 的上下文长度下，我的实现仍然能达到大约 20 tok/s 的解码速度。即使不使用 YaRN，将其
推到 Qwen 3.8 的完整原生上下文长度，它仍然可以达到大约 13 tok/s 的解码速度。

UD-Q3-K-XL 看起来太蠢了？好吧。

所以我再次尝试了更大的 UD-IQ4-XS 量化。更大的模型权重会使固定 KV 缓存可用的显存减少约 1 GB，
这意味着流式传输机制必须更早启动并处理更多 KV 数据。

然而，解码速度曲线仍然保持着非常稳定的斜率。

### 结论

- 这一改进主要惠及那些希望使用中端消费级 GPU 来托管强大的本地 LLM 以处理代理工作负载的用户。
- 假设您认为 15 tok/s 是保证与客服人员流畅在线聊天体验的最低可接受解码速度。使用我的实现方案，
  您可以将上下文压缩阈值设置为大约 20 万个 token，并且仍然能够高于该目标。
- 之前，可用上下文长度基本上受限于显存 (VRAM) 中键值缓存的物理容量（在我的 Q8 K / Q4 V 配置下
  大约是 10 万个令牌）。仅仅启用 UVM 并不能真正解决问题，因为一旦显存被过度占用，页面抖动就会
  严重影响解码性能。
- 采用自适应 KV 缓存流式传输，VRAM 限制不再是一道难以逾越的障碍。
- 我现在使用我的 RTX 5070 Ti 来运行 Qwen 3.8 27B UD-Q3-K-XL，它拥有完整的原生上下文长度，
  启用了 UVM，并且我的 Hermes 代理配置为在大约 200K 个 token 处进行压缩——而且它运行得出奇地好。
- 所以，只有 16GB 显存并不会自动让你失去参加本地 LLM 比赛的资格。

## 附录 B：CUDA Graph 与流式 KV 的动态替换（所有者提供，待代码验证）

以下为所有者提供的技术资料。它是设计假设和实现方向，不是 NInfer 现状的证明；
实现前必须在 NInfer 的 `decode_graph`、paged KV、block table、graph capture 代码中逐条核实。

### 一、CUDA Graph 的静态与动态边界

很多人以为“图一旦捕获，里面所有东西都焊死了，必须从头到尾一成不变”。事实并非如此。
要理解流式 KV 能否在 CUDA Graph 下动态替换，需要分清 CUDA Graph 固化了什么、允许动态改变什么。

| 维度 | 在 CUDA Graph 中是否静态？ | 为什么 |
|---|---|---|
| 拓扑结构（DAG） | 绝对静态 | 算子执行顺序、依赖边在捕获后固化，驱动借此消除 CPU 调度延迟 |
| Kernel 内部参数指针 | 默认静态 | 捕获时传给 kernel 的参数列表（如 `void*` 地址）被写进节点描述符 |
| 指针指向的显存数据 | 完全动态（运行时可变） | GPU 执行内核时，会去该指针指向的全局显存现读现算 |

流式 KV 不需要改动图的拓扑，它只需要内核“去读取流式进来的那一页”。这可以通过以下机制实现。

### 二、支持流式 KV 动态替换的核心原理

#### 1. 核心机制：内存间接寻址（PagedAttention 的 Block Table）

这是大模型推理引擎配合 CUDA Graph 的核心范式：

- 捕获阶段：Attention 内核的签名不是直接传 KV 显存首地址，而是传入一个预先分配好的页表指针：
  `paged_attention_kernel(..., int* block_table, ...);`
  在 CUDA Graph 建立时，`block_table` 的显存虚拟地址是固定不变的。
- 执行阶段：Graph 不知道也不在乎 `block_table` 数组里填的具体数字是多少。
  - 常规 decode：随着 token 增加，CPU 将新申请的页号写入这个数组。
  - 流式 KV 替换：假设第 12 层的第 50 个历史页被卸载到 Host，当前解码步它被拉回了显存的
    Ring Slot #2。你只需要在 launch 之前（或异步 H2D）将页表里的这一项改写：
    `block_table[layer=12][page=50] = Slot_2_Physical_Page_ID`
  - 当 CUDA Graph 里的 Attention 内核执行时，它解引用 block_table，动态查出当前这一页该去
    Slot #2 读。整个图既不需要重新捕获，也不需要任何驱动级开销，完成动态物理替换。

用户注：ninfer 文档提到 page IDs 是稳定输入数据、不是 graph key，且 block table publication
通过 pinned shadow 逐步 H2D 发布；这一点需要在 `docs/maintainer/paged-kv-cache.md` 和
`src/core/decode_graph.*` 中核实。

#### 2. CUDA 原生机制：节点参数原地打补丁（`cudaGraphExecKernelNodeSetParams`）

如果某种流式设计不走页表，而是想把 Attention 内核直接绑定的输入显存指针换掉，CUDA 原生也支持：

- NVIDIA 提供 `cudaGraphExecKernelNodeSetParams(graphExec, kernelNode, &newParams)`。
- 它允许直接修改已实例化图中某节点的入参（如更换 buffer 指针、更换 scalar 参数），
  不需要重新捕获，也不需要重新实例化整张图。
- 开销：单次节点参数修改约 0.5–1 微秒，远低于重新 capture 或普通 eager launch 的开销（5–20 微秒）。
- 不过在推理引擎中，机制 1（改 Block Table 显存）通常比机制 2 更快，因为改显存数据
  可以完全通过 GPU 异步流完成，连这 1 微秒的 CPU 驱动 API 调用都省了。

#### 3. 动态虚拟内存重映射（CUDA VMM：`cuMemMap`）

ninfer 现有的 `--vision-residency overlay`（平时在内存，用时借显存）底层用的就是 CUDA VMM：

- 原理：虚拟地址在 CUDA Graph 里始终固定，但底层绑定的物理页（`CUmemGenericAllocationHandle`）
  可以通过 `cuMemUnmap` / `cuMemMap` 动态切换。
- 局限：VMM 是操作系统和 GPU MMU 驱动级的映射，每次调用需要几十微秒，
  适合粗粒度的整图/整层借还（如视觉编码阶段）；对于每一步 decode 的微秒级循环，改页表（机制 1）更合理。

### 三、流式 KV 最关键的“另一半”：Graph 内跨流异步同步

流式传输不仅要求“换页”，还要求“算到第 l 层时，第 l+2 层必须刚好在后台从 Host 拷贝到显存完成，
不能发生数据竞争”。

普通 stream 模式下很容易（`cudaStreamWaitEvent`）。捕获进 CUDA Graph 后，图还能等外部流的传输吗？

答案：完全支持，依赖 `cudaGraphAddEventWaitNode`。

- 原理：CUDA Graph 原生支持多流捕获与事件节点（Event Node）。
  1. 捕获图时，Compute Stream 在执行到第 l+2 层的 Attention 计算节点之前，捕获一个 WaitEvent 依赖。
  2. 这会在 Graph DAG 内部生成一个 `cudaGraphEventWaitNode`。
  3. 执行时：专门的 Restore Stream 异步把第 l+2 层 KV 搬进 Ring Buffer，搬完后执行
     `cudaEventRecord`；Graph 内部运行到该节点时，由 GPU 硬件工作分发器自动等待该事件触发，
     随后立刻启动计算。
- 行业实战：vLLM、TensorRT-LLM 在处理 DeepSeek MLA / MoE 权重的重叠通信、双流并行时，
  都是把跨流事件捕获进 CUDA Graph 来掩盖传输延迟。

### 总结

回到问题：CUDA Graph 原理上支持流式 KV 的动态替换吗？

1. **寻址层面：完全支持。** 通过 Block Table 间接寻址，CUDA Graph 锁死的是页表指针，
   页表里的物理页号是纯显存数据，每步改写即可让内核读到流式页，完全规避图重捕获。
2. **流水线同步层面：完全支持。** 通过图内的 Event Wait Node，可以让 Graph 执行到特定层时
   硬件级等待外部 H2D 拷贝流完成，实现流式重叠。

因此，从 CUDA 底层原理看，CUDA Graph 不是流式 KV 的绊脚石；相反，正是它的 Block Table 机制和
Event Node 机制，让流式 KV 能以零 CPU 调度开销跑在微秒级 decode 循环里。
