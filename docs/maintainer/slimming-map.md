# 剪裁地图：复杂度在哪、哪些值得删、哪些不能碰

本文是给"只保留 27B + 16 GB 单卡 + 单并发"的派生分支用的**分析笔记**，不是产品契约。
数据来自本仓库当前代码的实测规模与阅读；规模只是"改动成本"的近似，判断以"删掉后是否减少状态"为准。

**先给结论**：架构不用重写，删"支持面"。删的顺序决定风险；每一刀之后必须重跑同一套等价用例。

---

## 1. 规模与复杂度分布（实测行数）

| 区域 | 规模 | 复杂度性质 | 对单卡单族单并发的价值 |
|---|---:|---|---|
| `src/ops`（783 文件，84 345 行） | 大 | **正当复杂度**：量化内核 × 层类型 × 架构档位 | **高**（这就是速度来源），但只保留你会跑的那几个 |
| `src/models`（247 文件，107 117 行） | 最大 | 五个族各自一套 executor/core | 只用一个族 ⇒ 其余整块可删 |
| `src/runtime`（62 文件，33 896 行） | 大 | 放置/缓存机、引擎循环、多卡 | 大量可删（见 §3.4） |
| `src/serve`（69 文件，23 598 行） | 中 | 协议翻译、槽位、流式 SSE、工具调用、视觉 broker | 只留本地单路径 |
| `src/core`（95 文件，22 283 行） | 中 | 分页 KV、宿主 arena、事件、KV 流式空间 | **几乎全留**（承重） |

## 2. 最复杂的三处（也是出 bug 的地方）

### 2.1 上下文缓存与放置（`src/runtime/engine/context_cache/**`，8 449 行）

私有目录、共享目录、会话索引、前缀索引、长锚点、端点锚点、turn closure、组合价值评估、
淘汰与替换、捕获事务、物化规划……**这些机制是为了"多请求、多前缀、可共享、可长期驻留"**。

对单并发本地使用：**收益接近零，风险最高**。本分支三个正确性缺陷（保留被当租约、空间倒回后
声明仍有效、规划期不校验可行性）全部出自这里与它的交界处。剪裁方向不是"修好每一个分支"，
而是**让分支不存在**：

- 一份私有 continuation、无共享前缀、无长锚点/分支锚点、无 turn closure；
- 新请求命中就复用、不命中就**替换**（同一槽位），不存在"并存"与"淘汰策略"。

### 2.2 多卡贯穿（`RankStreams`、stage、TP）

不是模块，而是**贯穿存储、执行、事务的类型**：`RankStreams` 出现在拷贝、事件、发布、消费的每一处。
删它不能"删目录"，只能：先删流水阶段与 TP 的模块和选项，再把 `RankStreams` 收敛成单流别名
（保留类型名，`operator[]` 恒返回 0 号流），最后靠编译器找出可以内联的地方。
**注意**：流式依赖"每流事件顺序"，不要把"多流"连同"多卡"一起删——单流仍然是"流"。

### 2.3 族的注册与前端共享

`src/models/registry.cpp` + 五个族目录 + 共用前端（tokenizer、chat template、工具调用、输出通道）。
删族是机械的；难的是**共用前端里的族方言**（每种模板/工具调用格式一个分支）。目标是：
一个前端、一个方言、一个模板。

## 3. 值得删的（按"删掉后减少多少状态"排序）

| # | 目标 | 动作 | 摩擦 | 风险 |
|---|---|---|---|---|
| 1 | 四个非目标模型族 | 整目录删除 + 注册表/CMake/测试项 | 低 | 低 |
| 2 | 推测后端（DFlash / DFlash2 / DSpark / ngram） | 只留一个（如 MTP），删其余的执行、组件、选项、报告字段 | 中 | 中（报告/测试引用多） |
| 3 | 共享前缀与锚点体系 | 删共享目录、长锚点、分支锚点、turn closure；`max_shared_prefixes=0` 变成"没有这个概念" | 中高 | **中高**（与放置、捕获、事务交织） |
| 4 | 流水阶段与 TP | 删 stage/rank 的模块、选项、启动规划 | 高 | 中（贯穿） |
| 5 | 多余架构档位 | 只留你的卡（+ 一个兜底）；删 route 表与 `if constexpr` 分支 | 中 | 低 |
| 6 | 多余 KV 格式 | 留 1–2 个；删其余 kernel 入口与选项校验 | 中 | 低 |
| 7 | serve 的多路径 | 只留本地单协议；删多协议翻译、视觉 broker（不用就不留）、槽位/多租 | 中 | 低 |
| 8 | 运行时校准/设备档案 | 用你卡上的一组常量替换运行时选择（仓库本来就为每张卡内置实测 route） | 低 | 低 |
| 9 | Hybrid 缓存模式 | 整块删（流式本来就拒绝它） | 低 | 低 |

## 4. 不能删的（承重）

1. **分页 KV 的块表间接寻址**（`src/core/paged_kv*`、`kv_stream_layout/slot_map`）——流式的窗口/环全靠它；
2. **pinned host 权威副本与 `HostKVArena`**——流式的物理基础；
3. **每流事件顺序**（`RankStreams` 的单流形态）——拷贝/消费/回写的正确性；
4. **注意力与 KV 量化的数学内核**（你实际会跑的那些）——这是性能本体；
5. **artifact 读取、物化、converter**（只留你的格式与模型）——入口；
6. **tokenizer / chat template / 输出通道**——用户可见面；
7. **观测字段**（`stream.upload_bytes`、`exposed_seconds`、`rounds_series`、`resident_pages`）——唯一的证据面，删了就再也说不清"快是因为少搬还是没搬"；
8. **等价性套件与 bench 脚本**（`tools/bench/run_kv_stream.py`、golden、`bench/results/kv-stream/*`）——剪裁过程的唯一安全网。

## 5. 每刀之后的验收（缺一不可）

- `check --suite equiv`（8 K / 100 K / 183 K，resident 与 streamed 各一臂）；
- C13：跨请求复用（`reused == retained_frontier`，且与冷跑逐位）；
- C14：几何不变（两种池形状 ⇒ ids 与 logprobs 逐位相同）；
- C15/C16：保留即缓存（任意下一请求都被接纳）+ 规划期可行（不出现"规划成功、执行才发现不可行"）。

这四项就是流式的契约。**剪裁中任何一项红了，先判定是"这刀删错了"还是"又露一条缝"**，
不要顺手改流式语义——两个变量一起动，出问题分不清账。

---

## 6. 与流式的关系（为什么剪裁就是在铺路）

流式的实现复杂度，主要不来自机制（宿主权威 + 窗口 + 环），而来自"它被接进了一套通用缓存机器"。
机器支持的每种形态，都是流式必须被证明安全的另一种状态。把形态收敛到一种（单族、单卡、单并发、
一份 continuation、命中即复用/不命中即替换），前面三个缺陷就变成**结构上不可能发生**，
而不是靠防御代码挡住。

剪到最后，"单 continuation、可替换"这条简化会变得几乎免费——它就是终态。
